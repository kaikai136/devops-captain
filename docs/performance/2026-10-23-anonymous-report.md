# 2026-10-23 部署性能实测报告

测试对象：172.16.0.161:30000，middleware 命名空间；日期按北京时间记录。没有应用测试账号，本次仅测试匿名 HTTP 路径并观察现有工作负载，未测试认证业务、批量主机采集、SSH/RDP 并发、数据库导入导出或浏览器渲染性能。未修改线上应用配置，未安装压力软件。

## 结论

当前服务资源占用低，没有证据表明 CPU 或内存已经耗尽。但 50 并发时尾延迟明显增加，共享会话场景出现一次 400，不能据此宣称可承载 50 个活跃业务用户。应优先检查会话写入和监控采集方式，再考虑扩容。

## 环境与基线

- Kubernetes 1.32，3 个节点；应用运行于 k8svip-161（4 核，约 7.3 GiB）。
- 单实例 Daphne、独立 Nginx、Redis、transfer-worker、guacd；数据库为 SQLite，Django Session 使用数据库后端。
- 基线 backend 96m / 98 MiB，worker 12m / 77 MiB，frontend 1m / 4 MiB，Redis 12m / 9 MiB，guacd 0m / 10 MiB。合计约 121m CPU / 198 MiB。
- 节点基线 CPU 15%，可用内存约 5.5 GiB，根分区使用率 34%。其他 Kubernetes 系统组件也占用节点资源。
- 测试期间已有用户每约 5 秒请求一次主机监控，结果包含这部分背景负载。

## 方法和数据

先做 10/25/50 并发短突发，再做每档约 20 秒的持续请求。客户端在本地 Windows，经 HTTP NodePort 访问。持续测试用 httpx AsyncClient 保持连接，每约 4 秒采集 kubectl top。Metrics API 是窗口平均指标，重复读取可能得到相同值；以下资源数值为观测样本最大值，不是瞬时峰值。

持续请求主测共享一个 Cookie jar，模拟同一会话并发，不等价于不同用户。滑块 GET 会写 Session，测试产生匿名会话和访问日志；未删除数据库记录。

## 资源和异常

- 观测 backend 达到约 638m / 147 MiB，仍低于现有 2 CPU / 2 GiB 上限；frontend 约 27m / 5 MiB。worker、Redis、guacd 基本稳定。
- 应用节点观测 CPU 约 32%，内存约 36%～37%；未观察到资源耗尽。
- 所有 Pod 保持 Ready，没有新增重启。frontend 原有一次启动期重启，本次没有增加。
- 健康检查在短突发各档结束后均返回 200。
- 共享会话 400 的对应日志包含 Django SessionInterrupted / UpdateError：请求完成前会话保存失败。不能仅凭该异常断言 SQLite 锁冲突，也未证明是真实会话被其他请求删除；需进一步复现。50 并发独立 Cookie 对照未复现 400。
- 测试后 backend CPU 已见回落至 242m，内存约 142 MiB；短时间内保留内存不代表泄漏。本次没有进行小时级稳定性测试。

## 优化方案

### 优先级 1：定位错误和改善观测

1. 用独立虚拟用户、独立 Cookie、预创建客户端和专用压测机复测；从 1/5/10/25/50 并发逐级持续 3～5 分钟，保留完整错误响应。分别直连 Service、NodePort 和用户入口比较，首页同样存在尾延迟，不能全部归因 Django。
2. Nginx 记录 request_time / upstream_response_time，应用记录请求 ID、路由耗时、数据库耗时和队列等待；不记录 Cookie、令牌或密码。接入 Prometheus/Grafana 或等效时序监控，记录 CPU throttling、RSS、工作集、文件描述符、连接数、SQLite 锁等待和健康检查。
3. 回归并发挑战、刷新挑战、登出与会话更新组合；针对 SessionInterrupted 定位具体保存失败原因。避免直接吞掉异常或放宽验证码验证。

### 优先级 2：会话和业务并发

1. 评估将 Django Session 从 SQLite 迁至专用 Redis 或 cached_db；先实现可配置后端并做登录、滑块、锁屏、双因素、会话审计回归。Redis 需要合理容量、淘汰策略和可用性；不能直接改为进程本地缓存。迁移可能使已有会话失效，需计划发布。
2. 多用户业务数据写入增长时迁移至外部 MySQL。当前不要在共享 SQLite hostPath 上直接增加多个 app 副本。
3. 单实例 Daphne 可在解决持久化和共享状态后评估多进程/多副本；先确认 LIVE_TERMINALS 等进程内状态，以及终端路由、共享文件、Redis Channels 和 worker 任务领取语义。未经验证不能只修改 replicas。
4. 滑块接口增加合理频率限制，防止匿名挑战持续创建数据库会话；定期执行 clearsessions 清理到期记录，避免清除仍有效的真实会话。

### 优先级 3：大量主机资源采集

源码 services/monitoring.py 每次采集调用 run_one_shot_ssh_command，建立新 SSH 连接，远端采样含 sleep 1，结束关闭连接。现有日志观察到约 5 秒一次采集。

- 100 台主机各每 5 秒采集意味着约 20 次连接/秒，仅 1 秒采样等待就形成约 20 个在途任务；不包含 SSH 握手和网络时间。这是估算，非实测容量。
- 按主机在 Redis 缓存 5～10 秒数据，同一主机多个页面共享结果；使用分布式锁合并重复采集，避免缓存失效时并发建连。
- 页面隐藏或离开时暂停轮询，增加随机抖动和失败指数退避。
- 将定时采集放入独立、有并发上限的 worker，HTTP 读取缓存；先从 5～10 个并发采集开始观察，配置连接/命令超时。
- 长期管理大量机器优先部署 node_exporter/agent，以中心采集或推送替代频繁 SSH 握手。SSH 连接复用需处理失效、权限和主机密钥校验。

### 优先级 4：资源保护与大任务

- 给 guacd 和 Redis 补充经实测调整的 requests/limits；Redis maxmemory 与容器上限之间留出 AOF/复制及运行开销。不能直接按本次空闲内存限制 RDP 峰值。
- transfer-worker 目前每秒轮询。空载 CPU 约 10～13m，不是主要负担；可将轮询间隔调整为 2～3 秒，接受任务启动延迟增加。大导入应保留流式处理、磁盘配额、超时和任务并发限制。
- SSH/RDP、大文件传输、录像需要单独测试并记录带宽、磁盘 IOPS、guacd 内存和 WebSocket 连接；本次没有应用账号和测试业务资源，因此没有容量结论。
- 不建议现在增加服务器内存或降低后端内存上限；先解决并发延迟和会话错误，之后进行 30～60 分钟稳定性复测。

## 下一轮验收建议

以真实业务 SLO 为准，可先采用试验门槛：10/25/50 独立用户、错误率低于 0.1%、常用轻接口 P95 小于 500 ms、节点 CPU 持续低于 70%、无 OOM/重启；需要先消除压测端瓶颈。本次不满足宣称“50 用户业务性能达标”的证据要求。
